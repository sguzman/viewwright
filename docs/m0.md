# M0 — Blueprint Embryo

M0 exists to prove that ViewWright can preserve useful UI design intent across multiple projections without becoming a low-level widget language.

## Required source concepts

M0 should parse and validate:

- one screen
- named regions
- named elements
- one composition tree
- semantic importance
- basic size intent
- spacing-token references
- design character / avoidances
- fixtures as named representative states

## Required internal concepts

The resolved model should make source conveniences explicit:

- stable IDs
- region ownership
- composition parent/child relationships
- resolved token references
- typed importance
- typed element kinds
- typed size intent
- diagnostics tied back to source concepts

The renderer and ASCII projector should consume the resolved model, not TOML syntax directly.

## Required projections

### 1. Structural inspection

A debug/tree view sufficient to inspect the resolved semantic model.

### 2. ASCII projection

A compact human-readable spatial sketch showing major regions, hierarchy, and representative elements.

It is acceptable for M0 ASCII geometry to be heuristic. It is not acceptable for the projector to invent semantic relationships absent from the model.

### 3. egui projection

A recognizable isolated rendering of the authored screen.

The egui projection need not be beautiful yet. Its purpose in M0 is to prove that the blueprint carries enough information to drive a real toolkit without degenerating into serialized egui calls.

## Initial specimen

`examples/project-browser.toml` is the first schema-pressure specimen.

It intentionally contains:

- navigation
- dominant primary content
- inspector
- a search element
- a collection
- a property sheet
- spacing tokens
- visual importance
- explicit design avoidances
- multiple fixtures

The specimen is allowed to change as implementation teaches us what is missing or incorrectly modeled. Changes should preserve the project's authoring-level boundary.

## Acceptance criteria

M0 is accepted when all of the following are true:

1. The project-browser specimen parses into typed Rust structures.
2. Invalid references and duplicate IDs produce useful diagnostics.
3. Token references resolve before projection.
4. The resolved blueprint can be printed as a semantic tree.
5. The ASCII projector emits a stable, understandable sketch from the resolved blueprint.
6. An egui preview host renders the same resolved blueprint without application-specific layout code.
7. The preview can select at least one named fixture.
8. Parsing/resolution and other non-trivial work are not performed as recurring heavy work on the render thread.
9. The implementation remains small enough that schema changes are cheap.

## Explicitly not required for M0

- responsive breakpoint language
- reusable authored components
- hot reload
- concept-art generation API
- ViewWitness comparison
- elaborate theme inheritance
- animation
- arbitrary application data binding
- production-quality renderer aesthetics
- multiple GUI backends

## First implementation shape

The likely Rust workspace shape is:

```text
crates/
  viewwright-model/     typed source + resolved model
  viewwright-ascii/     ASCII projection
  viewwright-egui/      egui projection
  viewwright-preview/   isolated preview application
```

This is a hypothesis, not sacred architecture. If M0 shows that fewer crates are clearer, collapse them.

## Stop condition before expansion

Do not broaden the language merely because a feature is imaginable.

After M0, the next schema work should be driven by a second real screen whose needs differ materially from the project-browser specimen.
