# M39 — v0.1.0 Release Readiness and Project Closure

## Context

M0 through M38 are accepted.

The core ViewWright 0.1 architecture is now complete:

```text
TOML authoring
    -> typed parse / validation / resolution
    -> semantic + ASCII + concept + layout projections
    -> egui rendering
    -> authored AccessKit observation identity
    -> ViewWitness Witness
    -> exact expectation / Witness verification
```

M38 proves that complete chain against real renderer output for ordinary, overlay, and overflow pressure surfaces.

The project should now stop expanding by inertia and establish a clean first release boundary.

## Why M39 exists

The implementation is ahead of some public-facing project documentation.

Concrete release-readiness pressure includes:

- the workspace already declares version `0.1.0`;
- README acceptance bookkeeping lagged Director acceptance before this authority commit;
- README, `docs/architecture.md`, and `docs/charter.md` still contain pre-bridge language such as "in time", "future", or "eventual" for capabilities now implemented through M33–M38;
- `docs/model.md` is an M0-era conceptual sketch containing candidate vocabulary and old future-tense statements that can be mistaken for current schema authority;
- the root manifest declares `license = "MIT"` but the repository currently has no root LICENSE file;
- there is no established v0.1 release note / changelog boundary;
- the only currently open product issue is the deliberately unpromoted responsive-layout roadmap, whose own promotion condition has not been met.

M39 closes documentation, packaging, and verification debt without adding product capability.

## Goal

Produce an audited v0.1.0 release candidate whose public project surfaces accurately describe the accepted implementation and whose workspace passes a stricter release-readiness check.

M39 does not implement another UI feature.

## Release boundary

v0.1.0 represents the accepted M0–M38 system.

The following remain explicitly outside v0.1.0 unless separately earned later:

- authored responsive layout / breakpoints;
- live ViewWitness observer/server orchestration;
- public runtime verification APIs;
- CI verification gates;
- screenshot/paint/raster comparison;
- fuzzy/tolerant comparison;
- richer fixture-aware expectation semantics;
- backend-independent element geometry;
- additional GUI backends;
- general application-state/data-binding systems.

Those are future possibilities, not unfinished v0.1.0 requirements.

## Release artifact policy

M39 prepares the release candidate but MUST NOT create or push the `v0.1.0` tag before Director acceptance.

After M39 is accepted, release finalization may create an annotated `v0.1.0` tag at the accepted commit and push it.

Do not create a GitHub Release or publish crates unless separately instructed. v0.1.0 is initially a repository release checkpoint, not a crates.io publication commitment.

## Product freeze rule

M39 should not change source schema, resolved semantics, layout behavior, renderer behavior, comparison behavior, ViewWitness behavior, or canonical specimens merely for cleanup.

If release checks uncover a real product defect requiring semantic or visible behavior changes, stop and report it instead of smuggling a new feature/fix into the closure milestone.
